# Integration guide

> **Not on npm yet.** The `npm install` commands and CDN URLs below work once 1.0.0 is published
> on npm; until then, build from source (see the root README, [Quick start](../README.md#quick-start)).

HPB Markup has **one renderer** (`@hpb/core`, a pure function from text to an SVG string) and thin
adapters for each host. Every adapter produces the same SVG, so a diagram looks identical in a web
page, a React app, a Next.js server component, a Markdown site or a file generated by the CLI.

| Host | Package | Entry |
| --- | --- | --- |
| Any JavaScript (Node, browser, workers, SSR) | `@hpb/core` | `renderSVG`, `validate`, `parse`, `buildModel`, `layout` |
| Plain HTML / CDN, no build step | `@hpb/web` | `<script src=".../hpb.min.js">`, `window.HPB`, `<hpb-diagram>` |
| Bundled web apps (Vite, webpack, Astro islands, ...) | `@hpb/web` | `import { HPB } from "@hpb/web"` or `import "@hpb/web/auto"` |
| React (Vite, CRA, Remix, ...) | `@hpb/react` | `<HpbDiagram />` |
| Next.js App Router | `@hpb/react`, `@hpb/react/server` | client component + `renderHpbToString` |
| Markdown (remark / unified, markdown-it) | `remark-hpb` | `remarkHpb`, `remark-hpb/markdown-it` |
| Terminal, CI, scripts | `@hpb/cli` | `hpb render`, `hpb validate` |

## Core API

```sh
npm install @hpb/core
```

```ts
import { renderSVG, renderDiagram, validate, parse, buildModel, layout, themes, HpbError } from "@hpb/core";

const source = `
hpb "Product A — firmware line"
line A "Product A"
release v1.0 @2026-01
improvement I-21 "Faster pairing"
issue X-101 "Crash on boot"
release v1.0.1 merges X-101
release v1.1 @2026-03 merges I-21
`;

const svg = renderSVG(source, { theme: "default" }); // string "<svg ...>...</svg>"
const problems = validate(source);                    // [] when valid
```

| Function | Returns | Notes |
| --- | --- | --- |
| `parse(text)` | `{ ast, diagnostics }` | Never throws. |
| `buildModel(ast)` | `HpbModel` | Checks the rules (R1–R3 in full, R4 as an open-branch release gate, R5–R7 in part, see [language.md §4](language.md#rules)); problems in `model.diagnostics`. |
| `layout(model, options?)` | `HpbLayout` | Pixel geometry, deterministic. Useful to draw with canvas, PDF, etc. |
| `renderSVG(textOrModel, options?)` | `string` | Pure string, no DOM. With errors: error-box SVG, or throws `HpbError` with `onError: "throw"`. |
| `renderDiagram(textOrModel, options?)` | `{ svg, diagnostics }` | Both in one parse (what `@hpb/react`, `@hpb/web` and `remark-hpb` use). |
| `validate(text, options?)` | `Diagnostic[]` | Parse + model diagnostics, sorted by line and column; with `options`, also `E-OPTION` warnings for bad option values. |
| `checkOptions(options)` | `Diagnostic[]` | Only the `E-OPTION` warnings (e.g. `theme: "drak"`, `colWidth: "abc"`). |
| `themes` | `Record<"default" \| "mono" \| "dark", HpbTheme>` | Read-only palettes (`"auto"` combines `default` and `dark`). |
| `version` | `"1.0.0"` | Language version. |

Options: `theme`, `showClosed`, `labels`, `colWidth`, `laneHeight`, `padding`, `fontFamily`,
`ariaTitle`, `idPrefix`, `showTitle`, `onError` — see
[language.md §7](language.md#7-options-config-and-themes). Options override `config` lines in the
source.

`@hpb/core` has **zero runtime dependencies**, ships ESM, CommonJS and an IIFE bundle
(`dist/index.global.js`, global `HPBCore`), and is side-effect free (tree-shakeable).

```js
// CommonJS
const { renderSVG } = require("@hpb/core");
```

Error handling:

```ts
try {
  const svg = renderSVG(source, { onError: "throw" });
} catch (e) {
  if (e instanceof HpbError) {
    for (const d of e.diagnostics) console.error(`${d.line}:${d.col} ${d.code} ${d.message}`);
  }
}
```

## HTML / CDN

No build step: one `<script>` tag. The bundle exposes `window.HPB`, registers the
`<hpb-diagram>` element and, when the page has loaded, replaces every
`pre.hpb`, `code.language-hpb` and `.hpb` block with its diagram (like Mermaid).

```html
<!doctype html>
<html>
<head><meta charset="utf-8"><title>Roadmap</title></head>
<body>
  <pre class="hpb">
hpb "Product A"
line A "Product A"
release v1.0
issue X-1 "Crash on boot"
release v1.0.1 merges X-1
  </pre>

  <hpb-diagram theme="mono" src="diagrams/product-a.hpb"></hpb-diagram>

  <script src="https://cdn.jsdelivr.net/npm/@hpb/web@1.0.0/dist/hpb.min.js"></script>
  <script>
    HPB.initialize({
      theme: "default",
      onNodeClick: (node) => console.log(node.kind, node.id), // { kind: "branch" | "baseline", id }
    });
  </script>
</body>
</html>
```

(unpkg works too: `https://unpkg.com/@hpb/web@1.0.0/dist/hpb.min.js`. Pin the version in
production and add a Subresource Integrity hash if your policy requires it.)

`HPB.initialize(config)` options: `startOnLoad` (default `true`; call
`HPB.initialize({ startOnLoad: false })` right after the script tag to opt out), `selector`
(default `"pre.hpb, code.language-hpb, .hpb"`), `interactive` (hover dimming, click and keyboard,
default `true`), `onNodeClick(node, container)`, `logErrors`, plus every core option.

Other calls:

| Call | Effect |
| --- | --- |
| `await HPB.run({ querySelector?, nodes?, force? })` | Render now (e.g. after inserting blocks); `force` re-renders. Resolves with `[{ element, svg, diagnostics }]`; rejects with the first `HpbError` when `onError: "throw"`. |
| `await HPB.render(id, code, options?)` | Resolves with `{ svg, diagnostics, bindFunctions }`; the DOM is not touched. `bindFunctions(element)` adds hover dimming and clicks once you have inserted the SVG. |
| `HPB.runSync(...)` / `HPB.renderSync(id, code)` | Synchronous versions (`renderSync` returns the SVG string). |
| `HPB.validate(code)` / `HPB.renderSVG(code)` | Core functions. |
| `HPB.defineElement(tag?)` | Registers `<hpb-diagram>` (done by the script bundle and `@hpb/web/auto`). |

### `<hpb-diagram>` custom element

```html
<hpb-diagram theme="default" fit>
  line A "Product A"
  release v1.0
  issue X-1 "Crash on boot"
  release v1.0.1 merges X-1
</hpb-diagram>
```

Renders in a Shadow DOM (page styles cannot break it). Attributes: `src` (URL of a `.hpb` file),
`theme`, `show-closed`, `labels`, `show-title`, `fit` (scale to the container width),
`no-interaction`. Property `code` sets the source from JavaScript; `svg` and `diagnostics` are
read-only. Events: `hpb-node-click` (`event.detail = { kind, id }`), `hpb-render`
(`{ svg, diagnostics }`), `hpb-error` (the `src` could not be loaded). Editing the text content
or an attribute re-renders automatically.

Before the script runs (or if it fails to load) the element is unknown to the browser and its text
shows as one run-together paragraph. Add this to the page CSS:

```css
hpb-diagram:not(:defined) { display: block; white-space: pre; visibility: hidden; }
/* or keep the source readable as a fallback: drop `visibility: hidden` */
```

`theme="auto"` follows the reader's light or dark mode without JavaScript (see
[Styling](#styling)). A bad attribute value (`theme="drak"`) falls back to the default and logs one
console warning.

### Coming from Mermaid

| Mermaid | HPB | Difference |
| --- | --- | --- |
| `mermaid.initialize(config)` | `HPB.initialize(config)` | Same idea; HPB's config also takes every renderer option. |
| `await mermaid.run({ querySelector, nodes })` | `await HPB.run({ querySelector, nodes, force })` | Resolves with one result per block. |
| `const { svg, bindFunctions } = await mermaid.render(id, code)` | `const { svg, diagnostics, bindFunctions } = await HPB.render(id, code)` | Adds `diagnostics`; never throws on bad input (unless `onError: "throw"`). |
| `await mermaid.parse(code)` | `HPB.validate(code)` | Synchronous; returns every diagnostic instead of throwing. |
| `<pre class="mermaid">` | `<pre class="hpb">`, `<code class="language-hpb">` | |
| — | `<hpb-diagram>` | A custom element, with `src=` for external files. |

## Bundlers and Vite

```sh
npm install @hpb/web
```

```ts
// Register <hpb-diagram> and auto-render blocks on load (side-effect import):
import "@hpb/web/auto";

// ...or control it yourself:
import { HPB } from "@hpb/web";
HPB.defineElement();
HPB.initialize({ startOnLoad: true, theme: "dark" });
```

Vite needs no configuration. To keep diagrams in their own files, import them as strings with
Vite's `?raw` suffix:

```ts
import roadmap from "./roadmap.hpb?raw";
import { renderSVG } from "@hpb/core";
document.querySelector("#roadmap")!.innerHTML = renderSVG(roadmap);
```

(For TypeScript, `declare module "*.hpb?raw" { const src: string; export default src; }` — Vite's
`vite/client` types already cover `?raw`.)

webpack 5 / Next.js: add `{ test: /\.hpb$/, type: "asset/source" }` to `module.rules` to import
`.hpb` files as strings. Turbopack (`next dev --turbopack`, the default in Next 16) ignores webpack
rules: add `turbopack: { rules: { "*.hpb": { loaders: ["raw-loader"], as: "*.js" } } }` (Next 15.3+;
`experimental.turbo` before) with `raw-loader` as a dev dependency. TypeScript needs the module
declaration from `examples/nextjs/hpb.d.ts`:

```ts
declare module "*.hpb" {
  const source: string;
  export default source;
}
```

In a server component you can skip all of this and read the file:
`readFileSync(path.join(process.cwd(), "roadmap.hpb"), "utf8")`.

## React

```sh
npm install @hpb/react react react-dom
```

```tsx
import { HpbDiagram } from "@hpb/react";
import source from "./roadmap.hpb?raw"; // Vite; or a string literal

export function Roadmap() {
  return (
    <HpbDiagram
      code={source}
      theme="default"
      showClosed
      onNodeClick={({ kind, id }) => openTicket(kind, id)}
      onDiagnostics={(all) => setProblems(all)}
      className="roadmap"
    />
  );
}
```

| Prop | Type | Notes |
| --- | --- | --- |
| `code` | `string` | HPB Markup source (required). |
| `theme` | `"default" \| "mono" \| "dark" \| "auto"` | Overrides `config theme`. `"auto"` follows `prefers-color-scheme`. |
| `showClosed` | `boolean` | Overrides `config showClosed`. |
| `labels` | `"full" \| "ref" \| "none"` | |
| `options` | `HpbOptions` | Any other core option (`colWidth`, `laneHeight`, `idPrefix`, ...). The id prefix defaults to a per-instance value from `useId()`, so the same source can be shown twice. |
| `onNodeClick` | `({ kind, id }) => void` | Click / Enter / Space on a branch or baseline. Makes nodes focusable buttons with an accessible name (the root becomes `role="group"`). |
| `onDiagnostics` | `(diagnostics) => void` | Called after **every** render with the full list: errors, warnings, `E-OPTION`, or `[]` once the source is clean. Use it to drive an error panel. |
| `onError` | `(diagnostics) => void` | Shortcut: called only after renders with errors (the error box is shown); not called on recovery. |
| `hoverDim` | `boolean` (default `true`) | Dim the other nodes to 35 % while hovering one. |
| other `div` props | | `className`, `style`, `id`, `aria-*`, ... go to the wrapping `<div>`. |

The component renders the SVG with `renderDiagram` during render (a pure function of the props and
of the `useId()` prefix, which React keeps identical on server and client), so it works with server
rendering and hydrates without mismatches; interactivity is attached in an effect after mount. It
is memoised on `code` and the options, and parses the source once for both the SVG and the
diagnostics.

Vite + React: nothing else to configure — see `examples/vite-react`.

## Next.js App Router

Two entry points:

- `@hpb/react/server` — `renderHpbToString(source, options)`: no React, no DOM, usable in **server
  components**, route handlers, `generateStaticParams`, edge and Node runtimes.
- `@hpb/react` — `<HpbDiagram>`, already marked `"use client"` in the build, for interactive
  diagrams in **client components**.

Server component (zero client JavaScript, the HTML contains the SVG):

```tsx
// app/roadmap/page.tsx
import { renderHpbToString } from "@hpb/react/server";
import { readFile } from "node:fs/promises";

export default async function Page() {
  const source = await readFile(process.cwd() + "/content/roadmap.hpb", "utf8");
  return (
    <div
      className="hpb-diagram"
      // A unique idPrefix per diagram when a page shows several (or the same one twice).
      dangerouslySetInnerHTML={{ __html: renderHpbToString(source, { idPrefix: "roadmap" }) }}
    />
  );
}
```

Client component (hover dimming and click):

```tsx
// app/roadmap/interactive.tsx
"use client";
import { HpbDiagram } from "@hpb/react";
import { useRouter } from "next/navigation";

export function InteractiveRoadmap({ source }: { source: string }) {
  const router = useRouter();
  return <HpbDiagram code={source} onNodeClick={({ id }) => router.push(`/items/${encodeURIComponent(id)}`)} />;
}
```

```tsx
// app/roadmap/page.tsx (server) passes the text down
import { InteractiveRoadmap } from "./interactive";
export default async function Page() {
  const source = await loadRoadmapFromCms();
  return <InteractiveRoadmap source={source} />;
}
```

The client component is still server-rendered on first load (the SVG is in the HTML), then
hydrated. A route handler can serve SVG files:

```ts
// app/api/hpb/route.ts
import { renderSVG } from "@hpb/core";
export async function POST(req: Request) {
  const svg = renderSVG(await req.text());
  return new Response(svg, { headers: { "content-type": "image/svg+xml; charset=utf-8" } });
}
```

See `examples/nextjs` (one server-rendered page, one interactive client page).

Pages Router: use `<HpbDiagram>` directly; it is SSR-safe.

### remark / unified (Astro, Docusaurus, Gatsby, custom pipelines)

```js
import { unified } from "unified";
import remarkParse from "remark-parse";
import remarkRehype from "remark-rehype";
import rehypeRaw from "rehype-raw";
import rehypeStringify from "rehype-stringify";
import remarkHpb from "remark-hpb";

const html = String(
  await unified()
    .use(remarkParse)
    .use(remarkHpb, { theme: "default" })
    .use(remarkRehype, { allowDangerousHtml: true })
    .use(rehypeRaw)
    .use(rehypeStringify)
    .process(markdown)
);
```

The fence becomes an mdast `html` node containing `<div class="hpb-diagram"><svg …></svg></div>`,
so the HTML stage must keep raw HTML (`allowDangerousHtml`, then `rehype-raw` or
`rehypeStringify({ allowDangerousHtml: true })`). Diagnostics become vfile messages with the line
of the Markdown file and the HPB code as `ruleId`.

Astro:

```js
// astro.config.mjs
import remarkHpb from "remark-hpb";
export default { markdown: { remarkPlugins: [remarkHpb] } };
```

MDX does not accept raw HTML nodes: in MDX files, import `<HpbDiagram>` from `@hpb/react` instead.

### markdown-it (VitePress, Eleventy, ...)

```js
import MarkdownIt from "markdown-it";
import markdownItHpb from "remark-hpb/markdown-it";

const md = new MarkdownIt().use(markdownItHpb, { theme: "default" });
md.render(source);
```

VitePress:

```js
// .vitepress/config.mjs
import markdownItHpb from "remark-hpb/markdown-it";
export default { markdown: { config: (md) => md.use(markdownItHpb) } };
```

Plugin options: every core option plus `languages` (default `["hpb"]`) and `className`
(default `"hpb-diagram"`, `false` for a bare SVG). Diagrams get unique ids within a document.

### Client-side Markdown (GitHub Pages, MkDocs, Hugo, Jekyll)

If you cannot add a build plugin, let the HTML stay as `<pre><code class="language-hpb">` and add
the script tag from [HTML / CDN](#html--cdn): `code.language-hpb` is in the default selector.

## CLI

```sh
npm install -D @hpb/cli
npx hpb render roadmap.hpb -o roadmap.svg --theme mono
npx hpb validate "docs/**/*.hpb"       # or let your shell expand the glob
cat roadmap.hpb | npx hpb render - > roadmap.svg
```

- `hpb render <in|-> [-o out.svg] [--theme default|mono|dark|auto] [--show-closed|--hide-closed]
  [--labels full|ref|none] [--col-width n] [--lane-height n] [--padding n] [--font-family css]
  [--aria-title text] [--id-prefix id] [--no-title] [--error-box] [--max n] [-q]`
- `hpb validate <in|-> [more...] [--format text|json] [--strict] [--max n]`
- At most 50 diagnostics are printed per file (`--max 0` prints all), and at most one syntax
  error per line; a file that is mostly not HPB Markup starts with `E-NOT-HPB`.
- Diagnostics: `file:line:col: severity [code] message` plus a source excerpt.
- Exit codes: `0` ok, `1` errors in the source (or warnings with `--strict`), `2` usage or I/O
  error. `render` does not write a file when the source has errors (unless `--error-box`).

CI example (GitHub Actions):

```yaml
- run: npx --yes @hpb/cli validate docs/diagrams/*.hpb --strict
- run: for f in docs/diagrams/*.hpb; do npx --yes @hpb/cli render "$f" -o "public/${f%.hpb}.svg"; done
```

Programmatic: `import { run } from "@hpb/cli"; const code = await run(["validate", "a.hpb"]);`.

## SSR notes

- `renderSVG` is a pure string function: no `window`, `document`, canvas or font metrics. It runs
  in Node 18+, Deno, Bun, edge runtimes, web workers and service workers.
- Output is **deterministic**: the same source and options give byte-identical SVG, so server and
  client renders match (no hydration warnings) and snapshot tests are stable.
- Text widths are estimated with built-in metrics (no DOM measuring). If you set a much wider
  `fontFamily`, increase `colWidth` slightly.
- Element ids default to a hash of the source. If the **same diagram appears twice in one page**,
  pass a distinct `idPrefix` to each `renderSVG` / `renderHpbToString` call. `<HpbDiagram>`
  (React `useId`), the auto-render, `<hpb-diagram id=...>`, `HPB.render(id, ...)` and the
  Markdown plugins do this for you.
- `@hpb/web` touches the DOM only when you call it; importing `@hpb/web` (not `/auto`) during SSR
  is safe. The `<hpb-diagram>` class is created lazily.
- For static sites, prefer rendering at build time (server components, remark, CLI) and add
  `@hpb/web` / `<HpbDiagram onNodeClick>` only where interaction is needed.

## Interaction in your own code

Every branch and baseline group in the SVG carries `data-hpb-kind` (`"branch"` or `"baseline"`)
and `data-hpb-id` (the id as written in the source). That is the whole contract:

```js
const root = document.querySelector("#roadmap");
root.innerHTML = renderSVG(source);

root.addEventListener("click", (e) => {
  const el = e.target.closest("[data-hpb-id]");
  if (el) console.log(el.dataset.hpbKind, el.dataset.hpbId);
});
root.addEventListener("pointerover", (e) => {
  const el = e.target.closest("[data-hpb-id]");
  const id = el?.dataset.hpbId;
  for (const n of root.querySelectorAll("[data-hpb-id]")) n.style.opacity = id && n.dataset.hpbId !== id ? "0.35" : "";
});
```

Or use the helper from `@hpb/web`: `attachInteraction(root, { onNodeClick, hoverDim: true })`
returns a function that removes the listeners. If you make nodes focusable yourself, also switch
the root from `role="img"` to `role="group"` and give each focusable group `role="button"` and an
`aria-label` (the text of its `<title>`): inside `role="img"` screen readers ignore the children.
`attachInteraction` does this for you and restores the static markup on detach.

Other stable hooks: root `svg.hpb.hpb-theme-<name>`; branches `g.hpb-branch.hpb-type-<type>.hpb-state-<state>`
(`merged`, `awaiting`, `open`, `targeted`, `discarded`) with id `<prefix>-b-<id>`; baselines
`g.hpb-baseline.hpb-kind-<kind>.hpb-status-<released|planned>` with id `<prefix>-v-<id>`;
`g.hpb-now`, `g.hpb-legend`, `g.hpb-note[data-hpb-ref]`; error output `svg.hpb.hpb-error`.

## Styling

The SVG carries its own colours (presentation attributes), so it looks right in emails, PDFs,
Markdown previews and `<img src="diagram.svg">`. Recommended container CSS:

```css
.hpb-diagram { overflow-x: auto; }           /* wide histories scroll instead of shrinking */
.hpb-diagram svg { display: block; max-width: none; }
/* or, to fit the width: .hpb-diagram svg { width: 100%; height: auto; } */
```

Pick `theme: "auto"` for sites with a light and a dark mode: the SVG carries both palettes and
switches with `@media (prefers-color-scheme: dark)`, also in server-rendered and static output. The
colours are CSS custom properties (`--hpb-background`, `--hpb-ink`, `--hpb-text`, `--hpb-main`,
`--hpb-issue`, ...) declared with zero specificity, so you can override them:

```css
.docs-dark svg.hpb { --hpb-background: #111827; --hpb-halo: #111827; }
```

Sites that switch the theme with a class instead of the media query can pass `theme: "dark"` or
`"default"` explicitly. Use `theme: "mono"` for print and greyscale documents. Sanitisers such as
`rehype-sanitize` remove `<style>` by default; allow it for SVG or the `auto` diagram stays light.

## Security

- **All text from the source is escaped** by `@hpb/core` (`&`, `<`, `>`, `"`, `'`) before it is
  written into the SVG: titles, labels, notes, rationales, ids, `ariaTitle`, `fontFamily`. The
  output contains no `<script>`, no event-handler attributes, no `<foreignObject>` and no external
  references, so injecting it with `innerHTML` / `dangerouslySetInnerHTML` / raw Markdown HTML is
  safe even when the source comes from users.
- This is why the Markdown plugins can ask for `allowDangerousHtml`: the only raw HTML they add is
  the SVG produced by the renderer; it does **not** make other raw HTML in your Markdown safe.
  Keep your sanitiser (e.g. `rehype-sanitize`) if authors are untrusted, and allow the SVG elements
  and attributes it needs, or run the sanitiser before `remark-hpb`.
- Do not concatenate untrusted strings into the SVG yourself; pass them through the source text.
- `<hpb-diagram src="...">` fetches with the page's normal CORS rules; only point it at trusted
  origins.
- Large inputs: if you render user input on a
  server, cap the source length (for example 100 KB) as you would for any parser.
